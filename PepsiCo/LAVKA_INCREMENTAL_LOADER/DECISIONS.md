# Основные решения

## 1) Без отдельного реестра файлов

Отдельная таблица-реестр не используется.  
Трекинг уже загруженных файлов реализован через поле `_source_file` в самих целевых таблицах.

## 2) Без отдельного SQL VIEW

Исторические данные хранятся в таблицах.  
Актуальный срез берется запросом с `row_number()` при чтении, без постоянного view-объекта.

## 3) Инкрементальная загрузка через append

Для фактов используется `write.mode("append")`.  
Это сохраняет все версии метрик и исключает потерю истории.

## 4) Учет 10-дневного weekly-перекрытия

Новые weekly-файлы могут содержать обновления за уже встречавшиеся даты.  
Они догружаются как новые версии строк с `_loaded_at`, поэтому история изменений доступна.

## 5) Идемпотентность на уровне файла

Новые файлы определяются через anti-join по `_source_file`.  
Fallback для старых таблиц без `_source_file`: отбор по `metric_date > max(metric_date)`.

## 6) Очистка staging без удаления папок

После выполнения ноутбука очищается содержимое staging-директорий в DBFS,  
но сами папки сохраняются для следующего цикла загрузки.
